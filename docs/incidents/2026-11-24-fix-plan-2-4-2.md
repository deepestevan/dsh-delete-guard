# 2.4.2 修复清单（据 2026-11-24 误伤摸排）

依据：`docs/incidents/2026-11-24-rule-false-positive-sweep.md`。
样本：62,131 条真实执行过的命令，误伤 432 条（0.70%）。

三份独立审计（两份逐条人工、一份代码级）＋ 机检复算。**本文件推翻了初稿的一个方向**，
保留推翻依据（§0）。

原则：**按"错了能不能被发现"划线，不按语法形态划线。** 不为了让数字变小而放松真会丢内容的形态。

## 0. 被推翻的初稿方向（保留反证）

初稿主张：`in-place-rewrite` 的判据改为"只有含区间切片/`-First`/`Select-Object` 这种丢弃形态才危险，
定点替换（`.Replace`/`-replace`）放行。

**否决。** 但本节初版写的三条"反证命令"**是错的**：它们的最小形态今天其实被**放行**，因为
规则 1 要求"同一文件既读又写"，而这三条在原样写法里读侧为空（复核 2026-11-25）：

| 最小形态（原稿所写） | 今天 |
|---|---|
| `$l = $l \| Where-Object { -not ($_ -like '*例题*') }; Set-Content $f $l` | **allow**（无读动词） |
| `for(...){ if($L[$i] -match '^### P\d+'){continue}; $out += $L[$i] }; Set-Content $f $out` | **allow**（无读动词） |
| `$t = $t -replace '(?s)^.*$','x'` | **allow**（无读动词） |

加上读前缀后才是危险形态，且确实被拒：

| 完整形态 | 今天 |
|---|---|
| `$l = Get-Content $f; $l = $l \| Where-Object { -not ($_ -like '*例题*') }; Set-Content $f $l` | **deny/in-place-rewrite** |
| `$L = Get-Content $f; $out=@(); for(...){ if($L[$i] -match '^### P\d+'){continue}; $out += $L[$i] }; Set-Content $f $out` | **deny/in-place-rewrite** |
| `$t = Get-Content $f -Raw; $t = $t -replace '(?s)^.*$','x'; Set-Content $f $t` | **deny/in-place-rewrite** |

结论不变（否决初稿方向仍成立），但**理由要换成正确的那个**：否决的依据不是这三条命令，
而是"写侧/读侧动词表在结构上不可闭合"——见下。

**真正的否决理由**：换成"丢弃形态清单"是把这个模块文件头
（`lib/rewrite-guard.js:21-29`）自己拒绝过的错重犯一遍（动词清单 → 形态清单，同一个洞换位置）。
机检可证的三处动词表缺口：

| 命令 | 今天 | 缺口 |
|---|---|---|
| `$f='a.md'; Set-Content $f (Get-Content $f \| Select-Object -First 10)` | **allow** | 读动词嵌在写语句**内部**，`readTargets` 只看语句首词 |
| `$f='a.md'; Set-Content $f ((Get-Content $f)[0..2])` | **allow** | 同上，且这是 2026-11-14 事故最紧凑的拼写 |
| `Select-String -Path a.md -Pattern 'x' \| Set-Content a.md` | **allow** | `readTargets` 对 `select-string` 用 `skip:1`，把 `-Path` 的值吃掉 |

这三条是本轮**新发现**的真漏洞（2026-11-25 复核），已列入 P0-4。

## P0 · `in-place-rewrite`：补两笔条件，不换判据

保留"读改写同一文件"作为**形状**判据（它对 2026-11-14 事故是准的），补两个可证伪条件。

### P0-1 顺序：读必须在写之前（收益约 318 条）

写**之后**的读是校验回读，其值不可能成为已完成写入的来源。

- 改哪里：`lib/rewrite-guard.js` 的 `inPlaceRewrite`（收集阶段）
- 怎么改：**逐文件（逐 key）**算 lastWrite，不用全局下标——一条命令里 A 先写、B 后读时，
  全局 `lastWrite` 会把 B 的读误算成"写后回读"。且 `lastWrite` 必须把
  `DOTNET_WRITE`（`lib/rewrite-guard.js:176`，用于 `.NET` 写）也算作"该语句有写目标"：
  `.NET` 写的动词不在 `WRITE_COMMANDS` 里，`writtenTargets` 对它返回 `[]`，否则
  `lastWrite` 会停在 `-1`，读集合被清空 → **`.NET` 读改写全体放行**（语料里 223 条此类）。
- **门闸**：含重复构造时不放行。词表必须覆盖 `for`/`foreach`/`while`/`do`/`until`/`switch`/
  `%`(ForEach-Object 别名)/`ForEach-Object`/`.ForEach(`/`1..n |`，且**只在这些词处于命令位或
  管道位时**才算（用 `commandWord`，不用全文正则）——全文正则会把 Python 字符串里的 `for` 误判。
- 保住：事故命令、`$c=Get-Content $f; Set-Content $f $c`、`Get-Content $f | Set-Content $f` 仍拒（已验）

### P0-2 可恢复副本：改语句级判定（收益 4 条，同时修 3 处过宽）

`hasCopyStep`（`lib/rewrite-guard.js:477-480`）现在是**全文短路**：
`BACKUP_MARKER.test(command)` 命中就豁免，早于任何分析。实测三种错误放行：

| 命令 | 今天 |
|---|---|
| `$f='a.md'; $t=Get-Content $f -Raw; Set-Content $f $t  # no .bak needed here` | **allow**（注释里的 `.bak`） |
| `$f='a.md.bak'; $t=Get-Content $f -Raw; Set-Content $f $t` | **allow**（目标名自带 `.bak`） |
| `$note='.bak is for wimps'; $f=Get-Content a.md -Raw; Set-Content a.md $f` | **allow**（无关字符串） |

改为三条同时成立：

1. **语句级识别副本**：某语句的写目标是 `<目标>.bak*` / `.tmp*` / `.new`，用现成的
   `exprKeys` 比对，**不用全文正则**。注意：**不要**简单把 `.tmp` 加进 `BACKUP_MARKER`——
   那只是把这条已存在的豁免通道再拓宽一档
2. **顺序**：副本写语句的下标必须 **< 目标写语句的下标`（只用到语句下标，可实现）
3. **副本路径 ≠ 目标路径**（堵掉"目标名自带 `.bak`"）

**降级**：初稿的"临时文件内容必须由原件读派生"**撤回**。它需要跨语句变量流分析，
而本文档 P2 已把同类能力（派生断言传播）判为"代价太高不做"——同一能力不能一处要一处不要。
且实测那 4 条 `fp:temp-then-verify` **全部已满足**该条件，加它零收益。
放行只需要"旧内容有处可还原"，不需要"副本由原件派生"（后者是质量问题）。

### P0-3 `.Replace` 放行条件改为编码连续性（收益约 183 条）

初稿条件是"次数校验"，评审实测它**挡不住它自己指出的风险**：

```
原文 GBK:  bed9c0fd…(举例)  →  -Raw utf8 读出 "����"
[regex]::Matches($raw, Escape('foo')).Count -eq 1  →  校验通过
写回后 CJK 全部变成 U+FFFD
```

字面量是 ASCII 时校验通过、编码仍被永久改写。**论证成立，但条件与论证不匹配。**

改为三条同时成立才放行：

1. 读侧**显式** `-Encoding`（或 `.NET` 读显式传 encoding）
2. 写侧**显式同名编码**（`Set-Content -Encoding` / `WriteAllText(path, text, $enc)`）
3. 变换是定点替换（`.Replace` / `-replace`），且不含区间切片

实测该条件下 `fp:point-edit` 可放行 **183 / 417（44%）**，比初稿的 7 条高一个量级，
且挡的正是编码风险本身。次数校验降为**理由文案里的建议**，不作放行条件
（初稿要求两侧都是字面量，而语料里 190/417 条是变量形参）。

**`-replace`（正则）仍不整体豁免**：正则作用域是整档，"恰好命中 1 次"不成立；
只有在上面三条（尤其显式编码）满足时才随同放行。

### P0-4 读动词嵌在写语句内部（新发现漏洞，非误伤）

`readTargets` 只看**语句首词**是否为读动词。读嵌在写语句里时读侧为空，规则 1 不触发：

| 命令 | 今天 | 备注 |
|---|---|---|
| `$f='a.md'; Set-Content $f (Get-Content $f \| Select-Object -First 10)` | **allow** | 整档重写 + 截断，一行写完 |
| `$f='a.md'; Set-Content $f ((Get-Content $f)[0..2])` | **allow** | 2026-11-14 事故最紧凑拼写 |
| `Set-Content notes.md (Get-Content notes.md \| Select-Object -First 3)` | **allow** | 同上，字面目标 |
| `Select-String -Path a.md -Pattern 'x' \| Set-Content a.md` | **allow** | `skip:1` 把 `-Path` 的值吃掉 |

语料里 0 条（尚未被踩到），正因如此更该补测试钉住。改法：收集读目标时对**整条语句**
扫读动词（含括号内嵌套），而不是只看首词。

## P1 · `-WhatIf`：修渲染，不摘语句（安全问题，不是误伤）

**实测的安全性倒转**：`Remove-Item -LiteralPath x.txt -WhatIf` → `rewrite/delete`，
而 rewrite 分支渲染成"去做真正的删除"（`lib/index.js:163-175`）。**用户要干跑，守卫让他真删。**

还有语义分裂：`Remove-Item -WhatIf x.txt` → `deny/opaque`（`-WhatIf` 吃掉路径），
`Remove-Item x.txt -WhatIf` → `rewrite`。

**初稿方案（按 flag 位置正则把语句从 `judged` 摘除）会开一个更严重的洞**，实测三条全部放行：

| 命令 | 摘除后 |
|---|---|
| `$f='a.md'; $t=Get-Content $f -Raw; Set-Content $f $t  # always -WhatIf first` | **allow**（注释里的词） |
| `$f='a.md'; Set-Content -LiteralPath $f -Value "run -WhatIf then finish"` | **allow**（值里的词） |
| `Remove-Item a.txt  # we used -WhatIf first` | **allow** |

经改正的方案：

- **不摘语句**。所有语句照常参与判定，只在 `lib/index.js` 的 rewrite 渲染分支区分干跑：
  若该语句带 `-WhatIf`，不生成 `file_trash` 指令，改为"这条是干跑；去掉 `-WhatIf` 才会真删"
- 干跑识别必须是 **token 级**：`-WhatIf` 是 `tokenize` 后的独立 token，且该 token
  不在 `#` 之后（`splitStatements` 不剥离注释，需显式检查）
- `-WhatIf:$false` / `-WhatIf:$true` 一律**不当干跑**（`:$false` 是真执行）
- 从 `FLAGS_TAKING_VALUE`（`lib/guard.js:68`）删掉 `-whatif`；同类误算还有
  `-confirm`/`-verbose`/`-debug`（都是开关不吃参数），实测 `Remove-Item -Verbose C:\x\a.txt`
  与 `Remove-Item -Confirm C:\x\a.txt` 都被判 `opaque`（目标被吃掉，模型拿不到可用指令）
- 必须同时覆盖 `decodedInlineBodies` 的解码后语句：`fp:dry-run` 里 3 条是
  `pwsh -Command "Clear-RecycleBin -Force -WhatIf"`，只改主语句路径修不到它们

验证：`Set-Content -Value 'run with -WhatIf first'` 不能被当干跑（需测试钉住）。

## P1 · 回收站：枚举 vs 驱动，并补两处真漏洞

`BIN_VERB_DRIVE`（`lib/guard.js:172`）把 `.Verbs()`（纯枚举）与 `.DoIt()`/`InvokeVerb()`（驱动）并列。

| 形态 | 现状 | 应为 |
|---|---|---|
| `$s.Namespace(10).Items() \| % { $_.Verbs() \| % { $_.Name } }` | deny | **放行**（只读） |
| `$i.InvokeVerb('Restore')` | allow | 放行（还原） |
| **`$i.InvokeVerb('delete')` 单发（无 Namespace 文本）** | **allow** | **必须拒** ← 真漏洞 |
| **`$i.Verbs() \| % { $_.DoIt() }`（无 Namespace 文本）** | **allow** | **必须拒** ← 真漏洞 |

改法：`&&` 条件放宽为"本语句引用 bin **或** 驱动实参是 delete/裸 DoIt"；
驱动时区分还原词（`还原|restore|estore`）与销毁词（`delete|删除`）。

**但"用全文还原词决定是否危险"会被注释骗**（实测）：

| 命令 | 判定 |
|---|---|
| `$s.Namespace(10).Items() \| % { $_.DoIt() }` | 拒 |
| `$s.Namespace(10).Items() \| % { $_.DoIt() }  # restore is a different verb` | **放行** |
| `$s.Namespace(10).Items() \| % { $_.DoIt() }  # 还原步骤见文档` | **放行** |

比现状更糟（现状一律拒）。定则：

- **`DoIt()` 永不放行**——它执行"当前选中的动词"，选中哪个不可判
- 放行只给：`Verbs()` 纯枚举、`InvokeVerb('<还原词字面量>')`

| 项 | 现状 | 改法 |
|---|---|---|
| **解构 spawn** `const {execSync}=require('child_process'); execSync('shred -u x')` | **allow（漏网）** | 匹配 `{…}=require('child_process')` 的赋值形态 + 变量在后续被调用；**不要**简单去掉 `SPAWN_CALL` 的前置点要求——那会让 `db.exec(…)`、`/re/.exec(…)` 在任何上下文命中 |
| `node -e "…dialect:'pwsh'…"` 正文含 `shred` 字样 | deny（误伤） | `SHELL_INTERPRETERS` 按**程序位**判定。**但先补上一条漏洞再改**：现在 `$shellPath='…\bash.exe'; & $shellPath -c "shred -u x"` 是 **allow**（变量名不含 `sh` 就漏），而 `$sh='bash'; & $sh -c "shred -u x"` 的 deny 靠的是变量名里碰巧有 `sh`。正确方向：程序位解析跟 `collectLiterals` 的单字面量赋值传播，**程序位是变量且不可解析 → 拒**（不可判），不是"不是 shell → 放行" |

| `Get-Content C:\x\run-iex-notes.md` | **deny/erase-api**（文件名含 `-iex`，`-` 是词边界） | `\biex\b` 需排除"位于文件路径/扩展名上下文"的匹配 |
| `Remove-Item variable:x` / `env:X` / `function:x` | 拒 → `file_trash("variable:x")`（**指令必然失败**） | `variable`/`env`/`function`/`alias` 放行 |
| `Remove-Item HKCU:\…` / `Cert:\…` | 拒 → `file_trash("HKCU:\…")` | 拒但**不给 file_trash 指令**，理由写"回收站管不了注册表/证书库" |
| `Remove-Variable` vs `Remove-Item variable:` | 一放一拦 | 统一 |
| 理由文案：33/78 条说"command substitution"而文本无 `$(` | 误导模型 | 变量操作数与命令替换分开写 |

## P2 · 不改（明确保留）

| 规则 | 为什么别动 |
|---|---|
| `slice-risk`（`OFFSET_ENDPOINT`/`COUNT_ARG`/`SAFE_PROVENANCE`） | 事故精确形态，含 `$idx=-1` → `$lines[0..-1]`；测试钉住文案不许提 `file_trash` |
| 无 token 的内容丢弃形态（`Where-Object` 过滤、`for+continue`、贪婪正则） | §0 的完整形态反证，正是这条规则存在的理由 |
| `erase-api` 的 `::Delete(` | 就是"无删除动词的 unlink"；`does-not-exist` 那条是我的分类器开的后门，不是规则误判 |
| `WIPE_FLAG_SHAPES`、`OPAQUE_CONSTRUCTS` 的删除目标判定、`SCRIPT_WRITE_*`、`FORBIDDEN_TARGETS` | 各自对（`real:script` 55 条抽样确为真内联删除） |
| `asserted-slice` 的派生断言传播 | 收益仅 2 条，需引入变量流分析；**不做**。同理 P0-2 的条件 3 也已撤回——同一能力不能一处要一处不要 |

**评审指出、但本方案仍未处理的**：`real:opaque` 79 条里约 70 条是误伤（89.7%），本文档只在
"不改清单"里一句"`OPAQUE_CONSTRUCTS` 各自对"，没有交代这 70 条为什么留着。
它是验收判据 A 达不到更低值的主因之一。**下一版（2.4.3）应单列 `opaque` 的位置判定**：
`$( … )` 出现在删除操作数位置才拒、here-string 正文先剥离、字面绑定的变量视为可枚举、
反引号转义与 `$( )` 区分。本次不做，是因为它独立于 `in-place-rewrite`，混在一起会让
改动面无法验证。

## 验收

初版的验收线（误伤 432 → <60，`real` 减少不得超过 5 条）**在算术上不可达，且用了一把有偏的尺子**：

- 各修复项收益相加：318 + 4 + 183 + 8 + 4 + 6 + 2 ≈ 525，但彼此重叠、且 P0-3 的 183 与
  P0-1 的 318 大量交叉，实际落在 **120 上下**，达不到 <60；
- "`real` 减少不得超过 5 条"与 P0-1 直接矛盾：P0-1 放行的 490 条里，分类器把 **314 条**
  标成 `real:whole-rewrite`——而抽样读原文，这些多数是"写后再读回校验"（如
  `python x.py 2>&1 | Out-File out.txt; Get-Content out.txt`），属分类器误判；
- `temp/sweep-241124/README.md` 自己写着"`fp:*`/`real:*` 是启发式产物，不是事实，不要只看合计数字"，
  而初版验收恰恰只看这个合计。

改为两条独立判据：

**判据 A（数量，宽松）**：误伤从 432 降到 **< 130**，并对放行集**人工抽查 ≥ 30 条**，
确认没有"同一文件、读前已存在、无副本、无显式编码保证"的形态被放行。

**判据 B（形态门禁，严格）**：以下形态的数量**一条都不得减少**（用改动前基线逐条比对）：

- `real:unchecked-slice` 63 条
- `real:opaque` 79 条（其中 8 条 NECESSARY 必须仍拒）
- `real:script` 55 条
- `real:delete` 62 条（扣除 `Remove-Item variable:` 这类 provider 目标）
- `real:erase` 7 条
- §0 的完整形态反证（加读前缀那三条）必须仍为 deny
- P0-4 新增的四条漏洞命令必须变 deny

**必须新增的测试**（每条一对一，正反各一）：

- `-WhatIf`：干跑不产生 `file_trash` 指令；注释/值里的 `-WhatIf` 不影响真实写入的判定
- P0-1：`.NET` 读改写仍拒；`%`/`do`/`switch` 循环内的读后写仍拒
- P0-2：注释里的 `.bak`、目标名自带 `.bak`、无关字符串里的 `.bak` 都**不再**豁免
- P0-3：显式编码放行；未显式编码的 `.Replace` 仍拒（含 GBK round-trip 用例）
- P0-4：四条嵌在写语句内部的读必须变 deny
- P1：`DoIt()` 带 `# restore` 注释仍拒；`$shellPath` 变量间接调用 bash 必须拒

命令执行：`node test/run-all.mjs` 全绿。
