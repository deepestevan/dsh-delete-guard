核心回收站护栏扎实，但覆写与脚本守卫在常规开发流上收得过紧

针对 DeepSeek Harness 插件 dsh-delete-guard（v2.4.4）的独立源码审查。覆盖 lib/index.js、lib/guard.js、lib/rewrite-guard.js、lib/staging.js、lib/shell-text.js 与 scripts/recycle-bin.ps1。

核心结论：你的直觉是准确的。插件把“强制文件删除走 Windows 回收站”这条底线守得非常稳，Win32 桥接与 UNC 暂存的工程完成度很高；但随着 rewrite-guard.js 与 blockScriptDeletes 不断加码，守卫已经从“拦截不可逆删除”越界到“静态审查常规代码编辑与测试脚本”，导致 Agent 在无破坏意图的日常工作中频繁撞墙。

Win32 回收站桥接与 UNC 暂存是插件最稳固的工程底座

从宿主接入方式看，插件没有采用脆弱的 ctx.shell monkey-patch，而是挂在 Cordis 宿主的 tools/pre-execute 瀑布流接缝上（lib/index.js），并配合 systemPrompt（order = 60）提前校准模型先验。这种“硬拦截 + 软引导”的组合，是你在 126 次真实拦截中实现 0% 彻底停工的关键。

底层执行层 scripts/recycle-bin.ps1 体现了对 Windows 文件系统坑点的深入实战经验：用无 BOM UTF-8 直接读取原始 stdin 流避开中文系统 OEM 代码页乱码；剥离 \\?\ 前缀避免 SHFileOperationW 报 0x7C；显式指定 Pack = 8 对齐 64 位结构；仅放行 NTFS/ReFS（防止 exFAT/FAT32 静默永久删除）；并逐条调用 SHFileOperationW(FOF_ALLOWUNDO) 以精确定位失败路径与尾随空格/点号（WSL 解压常见畸形文件名）诊断。

针对没有回收站的 UNC 网络共享，lib/staging.js 采用“先复制校验、再回收副本、最后删源”的顺序：拒绝内部符号链接/联接点（EREPARSE），校验本地卷剩余空间需满足 bytes * 1.02 + 64 MiB，并用 compareTrees 逐项核对相对路径与文件大小。虽然不保留 ACL/ADS（文档已诚实声明），但在策略层已做到安全闭环。

六大“收得太紧”的误杀热点正在拖慢 Agent 正常工作

仔细看 SECURITY.md 的统计数据：126 次拦截中只有 14% 转向了 file_trash，高达 78% 是 Agent 被拒后“换一种写法继续做”。当一个旨在把“删除”导向回收站的守卫，频繁拦截本不打算删除文件的编辑、测试和临时目录清理操作时，这 78% 里的很大一部分其实是在消耗不必要的试错轮次与上下文。

误杀热点 源码位置与触发条件 对正常 Agent 工作流的影响 摩擦级别
1. 无编码参数的 sed -i 原地替换 rewrite-guard.js：sedInPlaceTarget 同时记为读写目标，豁免需同时满足 hasBoundedSubstitution 与 hasPinnedEncoding。 POSIX/Git Bash 下 sed -i 's/a/b/g' file.txt 几乎不写编码参数，常规文本替换直接被拒，迫使 Agent 写临时文件或改工具。 高摩擦
2. 编写含清理逻辑的正常脚本/测试 guard.js：blockScriptDeletes 拦截写入 .ps1/.sh/.py/.js/.ts 且正文含 rm、fs.rmSync、shutil.rmtree 等词的操作。 Agent 为项目编写正常的 clean.js、teardown.sh 或需要清理临时目录的单元测试时，连“把代码写进文件”都会被拒。 极高摩擦
3. slice-risk 误伤新建文件写入 rewrite-guard.js：只要命令有任意 writtenTargets 且出现未校验 [$idx - 1] / -First ($n - 1)，即判定 slice-risk。 即使输出目标是全新的报表或临时文件（不存在覆写原文件风险），只要变量非 .Count 直接来源或未用正则匹配到的空值断言，整条命令被拒。 高摩擦
4. 循环体内先写后读失去豁免 rewrite-guard.js：检测到 for/foreach/ForEach-Object 时 hasRepetition = true，直接跳过 firstRead > lastWrite 豁免。 批量生成文件后立即回读校验的常规脚本被误判为“原地读写覆写”，无法利用写后验证豁免。 中摩擦
5. Git Bash /tmp/... 与通配符清理 guard.js：translatePosixPath 直接拒绝 /tmp/、~ 等非盘符路径；OPAQUE_CONSTRUCTS 拦截 -Recurse C:\tmp\*。 Agent 在 Git Bash 中创建临时目录测试并清理时被拒；清理 dist\* 或 tmp\* 需多轮先列举再逐个调 file_trash。 高摩擦
6. 歧义终端双方言交叉拒绝 index.js：shell、terminal_send、terminal_write 走 classifyAcrossShells 同时跑 pwsh 与 bash 判定。 若两种方言解析出的 rewrite 路径集合稍有差异，直接升级为 opaque 拒绝；且复合命令（如 npm run build && rm -rf dist）必须拆成多轮。 中摩擦

“在 sed -i 和单元测试脚本上严防死守，却让 git clean -fdx 直接从预过滤正则里滑过去，是当前安全边界最明显的不对称。”

词法正则护栏的边界与盲区

CHANGELOG.md 显示，仅 2.4.4 单个版本就封堵了 6 种绕过方式并移除了 5 类误报拒绝。这种“打补丁—修误报”的高频拉锯，本质上是把 shell-text.js 的词法切分与正则匹配当作完整 AST 解析器来使用的必然结果。

  • 高频真灾难盲区（git clean）：lib/index.js 的 MAY_TOUCH_FILES 预过滤根本不包含 git 子命令。社区里 Agent 清空未追踪工作区最常见的元凶之一就是 git clean -fdx 或 git reset --hard，当前守卫会直接放行。
  • PowerShell 反引号与动态别名：guard.js 依赖字面命令词匹配 PS_DELETE_VERBS，但 PowerShell 允许在命令名中插入反引号转义（如 R`emove-I`tem）或通过 New-Alias 临时别名绕过（SECURITY.md 已坦承动态拼接超出范围，但反引号属于静态可规范化形态）。
  • -WhatIf 逻辑轻微冗余：guard.js 在 classifyStatement 中对 -WhatIf 已直接返回 allow，而 index.js 的 rewrite 分支又保留了 isDryRun 拒绝并返回 DELETE_GUARD_DRY_RUN——导致纯 Remove-Item -WhatIf 放行，但混合语句中若有一条触发 rewrite 反而连 dry-run 一起拒绝。

分层放松方案：守住“回收站底线”，把正常开发权还给 Agent

建议保留 file_trash、trash_status、forbidEmptyRecycleBin、forbidWipe 与 UNC 暂存的全部刚性护栏，只针对“非删除类编辑”和“明确安全域的清理”做精确松绑。

优先级 目标模块 具体调整建议 预期效果
P0 rewrite-guard.js sed -i 's/.../.../' 在无整行删除（d）命令时直接放行，不再强制要求 hasPinnedEncoding；hasCopyStepFor 放宽对自定义备份目录/后缀（如 .v1、backup/）的识别。 消除 POSIX/Git Bash 下常规文本替换的反复撞墙，保留对无条件截断的拦截。
P0 rewrite-guard.js 将 slice-risk 的触发前提收窄为：写目标在命令中同时被读取（原地覆写），或通过轻量化检查确认目标文件已存在；写入全新输出文件时不再拦截切片。 避免正常数据处理与报表生成脚本因数组切片语法被误杀。
P0 guard.js 收窄 blockScriptDeletes：向工作区源码/测试文件（.py/.js/.ts）写入 fs.rmSync 或 shutil.rmtree 时放行，仅当同一条命令紧接着执行该脚本，或脚本写入系统/临时执行路径时拦截。 恢复 Agent 编写项目构建脚本与单元测试清理逻辑的能力。
P1 guard.js / index.js 在 translatePosixPath 中将 Git Bash 的 /tmp/... 映射到 Windows $env:TEMP 下的子路径并放行/重定向到 file_trash；对 C:\tmp\* 等明确临时目录下的浅层通配符尝试展开或引导，而非一律当 opaque 拒绝。 减少 Agent 在临时目录做实验与清理时的多轮试错。
P1 index.js / guard.js 在 MAY_TOUCH_FILES 中补入 \bgit\s+(?:clean|reset)\b，至少对 git clean -fd / -fdx 给出拦截或强提示（引导先 git status / 备份到回收站）。 补齐社区高频“清空未追踪工作区”盲区，提升真实防灾 ROI。
P2 guard.js 在 commandWord 阶段剥离 PowerShell 反引号转义；长期可考虑对超过 3 条语句的复杂 pwsh 脚本按需调用 [System.Management.Automation.Language.Parser]::ParseInput 替代继续堆砌正则。 终结“补丁—误报”循环，降低 1612 行正则引擎的长期维护成本。
